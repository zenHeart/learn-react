# 案例：最新选择不能被旧响应覆盖

## 来源与边界

这是根据真实岗位任务设计的教学案例，不是公司的面试原题。[Highbeam 前端岗位](https://jobs.ashbyhq.com/highbeam/2b4f6606-1289-4e85-8227-1290fe12f7f4)要求交付 React 功能并排查前端问题；该公开岗位材料于 2026-09-19 核验，仅代表国际资深岗位小样本。

机制依据为 [React 官方 Effect 数据获取说明](https://react.dev/reference/react/useEffect#fetching-data-with-effects)，核验日期 2026-09-19。网页是持续更新的文档；本案例的运行依赖锁定在项目 lockfile 中，不能用文档当前版本代替源码版本。请求控制器是教学模型，不是 React 调度器或完整的查询缓存库。

## 前置能力与任务

需要能够使用函数组件、state、Effect 清理、Promise 和 AbortSignal。打开站点首页的“完成业务任务 → 异步请求与竞态诊断”，或进入 `#/labs/async-race`。

用户先选择请求 1，随后选择请求 2。请求 2 先返回。即使请求 1 之后成功或失败，界面也必须保持请求 2 的结果；当前请求失败时应保留真实错误，不能用旧成功掩盖失败。重复相同查询参数时，也必须区分不同请求代次。

## 练习过程

1. **示范与预测**：保持修复关闭、运输层取消关闭，先预测最终结果。运行后读取事件顺序，说明响应到达顺序与用户选择顺序的区别。
2. **补全**：先只考虑旧成功迟到，写出允许发布状态的条件；再把同一条件应用到错误路径。
3. **独立完成**：关闭参考实现，在新文件重写请求控制器。不要仅比较查询 ID，相同资源的两次请求仍可能乱序。
4. **故障诊断**：分别删除代次检查、取消信号处理和销毁清理，找出能区分这些缺陷的测试。保留至少一个真实失败的回执。
5. **迁移**：换成搜索建议或分页列表，改变延迟和失败顺序；说明组件清理与共享查询缓存的生命周期有何不同。
6. **延迟复测**：间隔后从空文件复现，再用未见过的响应顺序验证。记录提示依赖，不能把点击实验通过当成独立掌握。

## 交付物与验收

交付请求控制器、测试、事件序列和一段机制解释。要证明旧成功、旧错误、相同参数重试、当前失败、卸载及取消行为；既检查最终结果，也检查等待期间不会闪现旧错误。

运行：

```sh
node --test src/demos/08.async/lab/request-latest.test.mjs
```

浏览器应真实复现故障版本的覆盖，再验证修复版本在“无法取消”的运输层仍保留最新结果。离开页面或改变实验条件后，旧任务不得继续发布状态，模拟计时器必须被清理。测试文件中的故障用例验证反例确实存在，不代表允许业务版本保留该故障。

本地实验使用 React 19.1.0 与 Node 24.20.0；最终发布仍须通过项目 CI、干净构建与线上交互验收。源码、测试、浏览器实验和学习者掌握程度分别记录。
