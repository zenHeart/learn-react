# 跨模块任务卡

这些任务需要独立作品和评审，不能以目录检查代替验收。先使用指定可运行起点，经过“示范 → 补全 → 独立 → 排错 → 迁移 → 三天后复测”。只使用合成数据，不提交真实凭据或客户材料。

## data-fetching-pattern：状态与缓存边界

前置：state、Effect、异步竞态。运行 `src/demos/08.async/lab/README.md`，再阅读 Context 与 Redux 的现有演示，以及固定快照中的 TanStack Query、Redux Toolkit、Zustand 文档。

把工单的输入草稿、筛选条件、共享主题和服务器列表分开列出所有者。先用已有实现交付，再选择一个合适工具重做远端缓存或客户端共享状态。交付方案表、代码、失效/重试测试与采用/放弃理由。验收：不能把不同服务器查询键混用；过期结果不得覆盖新查询；说明缓存失效、重试和卸载的责任。反例：用全局 store 保存所有输入，再解释它增加了哪些耦合。迁移：离线编辑与多标签同步；复测时解释哪些能力超出原方案。

## responsive-ui：窄屏业务任务

前置：组件、布局、表单。运行工单实验，在 390×844 与桌面尺寸完成创建、筛选、冲突和恢复，并在 200% 放大下复核。交付截图、操作记录及具体溢出定位。验收：主要动作可达、文本不被裁断、焦点清晰、错误与字段关联；不能仅拿首页截图证明任务通过。迁移：长标题、长错误与翻译文本；三天后独立修复陌生溢出。

## touch-interactions：多输入方式

前置：事件与语义 HTML。运行可访问性对话框示例，用触控与键盘完成相同确认任务。交付交互表、取消/确认测试及辅助技术观察。验收：无 hover-only 动作、对话框关闭后焦点恢复、Escape 取消不会误提交、背景内容不可被模态操作误触。迁移：危险操作的二次确认与撤销。屏幕阅读器结论必须记录实际工具和版本，未做则写未核验。

## architecture-review：基于约束的方案评审

前置：业务交付、状态、测试。以工单模块为底稿，与固定 Bulletproof React 快照比较组织方式。约束：两人团队、两个页面、未来可能跨模块共享；随后改为多团队产品。交付模块依赖图、两个候选方案、最小试验、维护成本与反例。验收：每个抽象解决明确问题；区分数据获取、领域规则和展示；测试能隔离失败原因。迁移：服务拆分或国际化，重新评估原选择。社区目录树不作为强制标准。

## migration-strategy：框架增量迁移

前置：路由、异步、SSR/RSC。运行独立 Next 案例，选一个当前静态页面迁移为服务端课程页。交付分阶段计划、缓存正确性测试、公开数据 DTO、回滚步骤和一次本地演练。验收：旧深链可用，交互保持，故障可回退，合成服务端标记未进入浏览器。反例：把整个应用加上 `'use client'` 后说明失去了哪些边界。迁移到另一框架时重核合同，不能套用 Next 版本特性。
